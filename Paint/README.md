# Paint для MIK32V2

**Встраиваемый графический редактор на C для MIK32V2 с TFT-дисплеем 480×320 и резистивной сенсорной панелью.**

  <img src="<img width="664" height="450" alt="2026-10-07_17-08-21" src="https://github.com/user-attachments/assets/b321d90e-637a-48ed-a6cb-cae87dea684e" />" alt="Основной интерфейс Paint" width="360">

Проект разработан с учётом жёстких ограничений микроконтроллера: **32 МГц, 16 КБ RAM, ограниченный Flash и отсутствие ресурсов для полноэкранного framebuffer**.

Основная архитектурная идея проекта — **не хранить готовое изображение целиком в памяти**, а сохранять геометрию нарисованных штрихов и параметры кисти.

## Назначение

Paint — это не desktop-графический редактор, перенесённый на микроконтроллер.

Архитектура изначально построена вокруг ограничений embedded-системы:

- RAM — 16 КБ;
- CPU — 32 МГц;
- дисплей — 480×320;
- сенсор — резистивный;
- изображение передаётся по SPI;
- для больших операций используется DMA;
- динамическое хранение полного изображения не используется;
- состояние рисунка имеет фиксированные верхние границы.

Это определяет практически все ключевые решения проекта: формат истории, алгоритмы геометрии, обработку touch, перерисовку и работу с LCD.

# Обработка касаний

Touch-пайплайн построен в несколько этапов.

```text
          raw X/Y
             |
             v
      несколько выборок
             |
             v
          averaging
             |
             v
       noise filtering
             |
             v
       jump validation
             |
             v
     raw -> screen coords
             |
             v
       Paint state machine
             |
       +-----+------+
       |            |
       v            v
     toolbar       canvas
                      |
                      v
                    stroke
```

## Усреднение

Количество выборок:

```c
#define TOUCH_FILTER_SAMPLES  4
```

Полученные значения усредняются перед дальнейшей обработкой.

Это уменьшает влияние небольшого шума резистивного сенсора.

---

## Подтверждение касания

Для определения начала и конца касания используются отдельные счётчики подтверждения:

```c
#define TOUCH_PRESS_CONFIRM_SAMPLES    3
#define TOUCH_RELEASE_CONFIRM_SAMPLES  2
```

То есть одиночная нестабильная выборка не должна мгновенно менять состояние интерфейса.

---

## Фильтрация скачков

Для координат используется порог:

```c
#define TOUCH_NOISE_THRESHOLD 2
#define TOUCH_MAX_JUMP        400
#define TOUCH_MAX_JUMP_SQ     (TOUCH_MAX_JUMP * TOUCH_MAX_JUMP)
```

Последний параметр используется в квадрате расстояния, поэтому для проверки расстояния не требуется `sqrt()`.

Это особенно важно для микроконтроллера, где лишняя плавающая арифметика не нужна.

---

## Калибровка

Raw-диапазон задаётся в `touchpad.h`:

```c
#define TOUCH_MIN_RAW_X  150
#define TOUCH_MIN_RAW_Y  100
#define TOUCH_MAX_RAW    1960
```

После преобразования координата приводится к пространству дисплея:

```text
raw touch coordinates
        |
        v
 calibration
        |
        v
screen coordinates
        |
        +--> X: 0..479
        |
        +--> Y: 0..319
```

Размер экрана:

```c
#define TOUCH_SCREEN_WIDTH   480
#define TOUCH_SCREEN_HEIGHT  320
```

# Состояния интерфейса Paint

`paint.c` использует явное состояние текущего touch-действия.

Основные действия представлены отдельными состояниями:

```c
PAINT_TOUCH_NONE
PAINT_TOUCH_CANVAS
PAINT_TOUCH_CLEAR
PAINT_TOUCH_BRUSH
PAINT_TOUCH_RGB
PAINT_TOUCH_MENU
PAINT_TOUCH_PIPETTE
PAINT_TOUCH_BRUSH_2
PAINT_TOUCH_MENU_2
PAINT_TOUCH_UNDO
PAINT_TOUCH_REDO
```

Это позволяет разделить:

- начало касания;
- движение;
- удержание;
- отпускание.

Критически важный принцип:

> Действие кнопки определяется по координате начала касания, а не по текущему положению пальца.

Например, если пользователь начал рисовать на холсте и затем провёл пальцем в сторону Undo, это не должно превращаться в команду Undo.

---

# Одноразовые действия

Для Undo и Redo используется отдельный флаг:

```c
paint_touch_action_done
```

Логика:

```text
touch start
     |
     v
Undo / Redo
     |
     v
action_done = 1
     |
     v
holding finger
     |
     +----> action не повторяется
     |
touch release
     |
     v
action_done = 0
```

Таким образом, удержание пальца на кнопке не вызывает несколько последовательных операций Undo или Redo.

# Модель хранения рисунка

Полный framebuffer для изображения 480×320 в RGB565 потребовал бы:

```text
480 × 320 × 2 = 307 200 байт
```

Это значительно больше доступных 16 КБ RAM.

Поэтому framebuffer всего холста в проекте не используется.

Вместо этого хранится **история штрихов**.

---

## Точка

```c
typedef struct
{
    int16_t x;
    int16_t y;
} PaintHistoryPoint;
```

Одна точка занимает:

```text
X = 2 байта
Y = 2 байта

Итого = 4 байта
```

Максимальное количество:

```c
#define PAINT_HISTORY_MAX_POINTS 1500
```

Память:

```text
1500 × 4 = 6000 байт
```

---

## Штрих

```c
typedef struct
{
    uint16_t first_point;
    uint16_t point_count;
    uint16_t color;
    uint16_t brush_size;
    uint8_t  brush_type;
} PaintHistoryStroke;
```

Штрих содержит:

- индекс первой точки;
- количество точек;
- RGB565-цвет;
- размер кисти;
- тип кисти.

Максимальное количество штрихов:

```c
#define PAINT_HISTORY_MAX_STROKES 128
```

---

# Почему хранится именно история штрихов

Вместо:

```text
canvas -> pixels -> framebuffer
```

используется:

```text
stroke 0
  ├── point
  ├── point
  └── point

stroke 1
  ├── point
  ├── point
  └── point

stroke 2
  └── ...
```

Это позволяет:

- не хранить 300+ КБ изображения;
- реализовать Undo без копирования всего экрана;
- реализовать Redo;
- выполнять повторную растеризацию;
- получать цвет под курсором из геометрии рисунка.

Цена этого подхода — необходимость повторной отрисовки истории после операций, изменяющих видимый набор штрихов.

Для данного класса embedded-систем это разумный обмен **RAM на CPU/SPI time**.

---

# Отрисовка штрихов

Непрерывный штрих строится по последовательности touch-точек:

```text
P0 -> P1 -> P2 -> P3 -> P4
```

Между последовательными точками строятся сегменты:

```text
P0 -------- P1
             \
              P2
               \
                P3
```

Для дискретной растеризации используется целочисленный алгоритм построения линии.

Преимущество такого подхода:

- нет необходимости использовать floating point;
- координаты остаются целочисленными;
- хорошо подходит для небольшого MCU;
- один и тот же принцип может использоваться при восстановлении истории.

# Формы кисти

## Square

Рисуется прямоугольная область вокруг точки.

## Circle

Используется радиальная геометрия относительно центра кисти.

## Ellipse

Размер по X и Y может отличаться.

## Spray

Растеризуется набор точек вокруг центра.

Таким образом, brush renderer отделён от обработки touch: touch сообщает координаты, а `touchpad.c` превращает координаты в конкретную геометрию кисти.

# Undo / Redo

Undo/Redo реализованы поверх истории штрихов.

Упрощённая модель:

```text
             history
                |
     +----------+----------+
     |                     |
 all stored strokes    visible strokes
                           |
                    +------+------+
                    |             |
                   Undo          Redo
                    |             |
                    v             v
                 count--       count++
```

При Undo:

1. уменьшается количество видимых штрихов;
2. текущий touch-stroke завершается;
3. холст восстанавливается из оставшейся истории.

При Redo:

1. количество видимых штрихов увеличивается;
2. изображение повторно растеризуется.

Главное преимущество — не требуется хранить отдельные копии изображения для каждого состояния.

---

# Пипетка

Пипетка также не использует framebuffer.

Для поиска цвета вызывается:

```c
int paint_history_pick_color(
    int x,
    int y,
    uint16_t *color
);
```

Поиск выполняется **от последнего штриха к первому**.

Это соответствует модели рисования:

```text
старые штрихи
      |
      v
новые штрихи
      |
      v
     top
```

Если несколько штрихов пересекаются, верхним считается последний нарисованный.

---

## Проверка попадания в сегмент

Для линейного сегмента сначала используется bounding-box rejection.

Если точка потенциально находится рядом с сегментом, применяется геометрическая проверка расстояния до сегмента.

Сравнивается квадрат расстояния:

```text
distance²
```

а не:

```text
sqrt(distance²)
```

Это исключает ненужный `sqrt()`.

# RGB-редактор

Цвет хранится как три независимых 8-битных компонента:

```c
static uint8_t paint_rgb_red;
static uint8_t paint_rgb_green;
static uint8_t paint_rgb_blue;
```

Пользователь выбирает:

```text
R = 0..255
G = 0..255
B = 0..255
```

Перед выводом на дисплей цвет переводится в RGB565.

---

## RGB565

LCD работает с 16-битным цветом.

Формат:

```text
RRRR RGGG GGGB BBBB
```

То есть:

- Red — 5 бит;
- Green — 6 бит;
- Blue — 5 бит.

RGB-редактор при этом работает с полноценными 8-битными компонентами, а преобразование выполняется непосредственно перед выводом.

---

# Оптимизация RGB-меню

При движении пальца по RGB-слайдеру нет необходимости перерисовывать всё меню.

Вместо:

```text
полная перерисовка RGB menu
```

используется:

```text
изменился Red
     |
     +--> очистить старый Red slider
     |
     +--> нарисовать новый Red slider
     |
     +--> обновить preview
```

Аналогично для Green и Blue.

Это уменьшает объём данных, передаваемых в LCD.

# Частичная перерисовка

History содержит функцию:

```c
void paint_history_redraw_area(
    int x_min,
    int y_min,
    int x_max,
    int y_max
);
```

Она используется там, где достаточно восстановить только часть изображения.

Общий принцип:

```text
полный холст
+------------------------------+
|                              |
|        изменённая область    |
|           +-------+          |
|           |       |          |
|           |       |          |
|           +-------+          |
|                              |
+------------------------------+

Перерисовывается не весь экран,
а только необходимая область.
```

Перед растеризацией сегмента можно выполнить быструю проверку его положения относительно области.

Это особенно полезно для UI-операций, когда изменение затрагивает небольшой участок.

# LCD и DMA

LCD использует RGB565 и передачу по SPI.

Для больших одноцветных областей используется DMA.

Размер экрана:

```c
#define TFT_WIDTH   480
#define TFT_HEIGHT  320
```

DMA-буфер:

```c
#define DMA_BUFFER_SIZE (TFT_WIDTH * 3)
```

То есть:

```text
480 × 3 = 1440 байт
```

Буфер рассчитан на одну строку передачи и используется повторно.

Это принципиально отличается от framebuffer:

```text
framebuffer:
480 × 320 × 2 = 307 200 байт

DMA line buffer:
480 × 3 = 1 440 байт
```

Таким образом, DMA используется как средство ускорения передачи, а не как хранилище всего изображения.

---

# Почему DMA здесь важен

Большие прямоугольные области возникают, например, при:

- очистке холста;
- очистке меню;
- перерисовке фона;
- восстановлении областей интерфейса.

Вместо последовательной генерации каждого пикселя CPU может подготовить повторяющиеся данные и передать блок через DMA.

Это снижает нагрузку на CPU и уменьшает количество программных операций на пиксель.

---

# Использование памяти

Фактический `.map` текущей сборки позволяет отдельно увидеть основные статические объекты.

### Основные буферы

| Объект | Размер |
|---|---:|
| `dma_buffer` | 1440 B |
| `paint_history_strokes` | 1280 B |
| `paint_history_points` | 6000 B |

История:

```text
points:
1500 × 4 = 6000 B

strokes:
128 × 10 = 1280 B
```

В текущей сборке linker map показывает:

```text
.bss = 0x23E4 = 9188 B
```

При этом:

```text
RAM = 16 KiB = 16384 B
```

Конец статически размещённых данных:

```text
_end = 0x02002944
```

Стек конфигурируется размером:

```text
0x400 = 1024 B
```

Linker script проверяет, чтобы статически размещённые данные не пересекались с областью стека.

Это важная часть проекта: память контролируется не только логически, но и на уровне итоговой линковки.

# Инженерные решения

## 1. Нет framebuffer

Полный framebuffer для 480×320 RGB565 слишком велик для 16 КБ RAM.

Вместо этого:

```text
history of strokes
        +
small DMA buffer
        +
direct LCD rendering
```

---

## 2. История вместо снимков экрана

Для Undo/Redo не создаются копии всего экрана.

Сохраняется описание штриха:

```text
points
color
brush size
brush type
```

Это позволяет получить предыдущую версию изображения повторной растеризацией.

---

## 3. Статические ограничения

Основные структуры имеют фиксированный максимальный размер.

Это делает использование памяти предсказуемым и не требует сложного управления heap.

---

## 4. Целочисленная геометрия

Для базовой растеризации используются integer arithmetic и сравнение квадратов расстояний.

Это уменьшает стоимость вычислений на MCU.

---

## 5. Частичное обновление

Если изменился один элемент интерфейса, по возможности обновляется только этот элемент.

Пример — RGB slider:

```text
old slider
   |
   v
clear old area
   |
   v
draw new slider
   |
   v
draw color preview
```

---

## 6. Разделение уровней

Низкоуровневая работа с железом не смешана с UI:

```text
hardware
   ↓
LCD / SPI / DMA / Touch
   ↓
drawing primitives
   ↓
paint history
   ↓
Paint UI
```

Это упрощает изменение отдельного слоя без переписывания остальных.

# Жизненный цикл штриха

Новый штрих начинается в момент первого касания холста.

```text
touch start
    |
    v
paint_history_start_stroke()
    |
    v
paint_history_add_point()
    |
    v
paint_history_add_point()
    |
    v
paint_history_add_point()
    |
    v
touch release
    |
    v
paint_history_end_stroke()
```

При этом параметры кисти сохраняются вместе со штрихом.

Это важно для восстановления изображения: старый штрих должен быть перерисован с теми же параметрами, с которыми он был создан.

---

# Очистка холста

Очистка выполняется не удалением пикселей из некоторого framebuffer.

Вместо этого:

1. очищается history;
2. LCD заполняется фоновым цветом;
3. интерфейс Paint отрисовывается заново;
4. состояние открытых меню сбрасывается.

Таким образом, графическое состояние и UI-состояние остаются согласованными.

---

# Что является наиболее ресурсоёмким

Для данной архитектуры основные потребители RAM — это:

```text
paint_history_points
paint_history_strokes
dma_buffer
HAL / SPI state
stdio / runtime state
```

Поэтому дальнейшая оптимизация проекта в первую очередь должна учитывать:

- количество точек истории;
- размер DMA-буфера;
- локальные массивы;
- стек;
- дополнительные глобальные структуры.

Добавление framebuffer даже небольшого размера требует отдельно оценивать RAM budget.

---

# Ограничения текущей архитектуры

Архитектура имеет сознательные компромиссы.

### Ограниченная история

Количество точек:

```c
PAINT_HISTORY_MAX_POINTS = 1500
```

Когда история заполнена, новые точки не могут сохраняться бесконечно.

### Стоимость восстановления

Undo/Redo требуют повторной отрисовки истории.

Чем больше сохранённых штрихов, тем больше работы необходимо выполнить для восстановления изображения.

### Зависимость от скорости LCD

Даже при оптимизированной CPU-части финальная скорость отображения ограничивается пропускной способностью SPI/LCD.

Поэтому частичная перерисовка и DMA являются не декоративными оптимизациями, а частью общей архитектуры.

# Принцип проектирования

Главный принцип проекта можно сформулировать следующим образом:

```text
Не пытаться компенсировать ограниченность RAM
большими буферами.

Вместо этого:
    хранить компактное состояние,
    вычислять только необходимое,
    передавать только необходимое,
    перерисовывать только необходимое.
```

Именно поэтому Paint построен вокруг:

- stroke history;
- integer rasterization;
- touch filtering;
- partial redraw;
- DMA;
- RGB565;
- статических буферов;
- явной state machine интерфейса.
